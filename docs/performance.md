# 性能与磁盘影响

DiskWatch 的实时监控基于文件系统事件，只在事件到达后读取路径、大小和时间等元数据，
不会读取文件内容。正常运行不会像表面扫描或坏道检测那样持续顺序读取整块磁盘。

## 控制策略

- 同一路径连续修改先合并，默认停止写入约 6 秒后才读取最终大小。
- watchdog 回调只做安全路径判断和入队，SQLite 使用批量事务和 WAL。
- 队列到达高水位时合并修改事件；队列满时明确计入丢弃统计，不阻塞文件系统线程。
- 启动优先使用 NTFS USN 日志恢复离线变化；不可用时默认只补扫用户目录，不默认全盘补扫。
- 补扫只读取目录项和文件元数据，不读取文件内容。
- 补扫线程在 Windows 上降为低于正常优先级，界面持续显示进度并可取消；设置中可在用户目录和全部监控根目录之间明确选择。
- 活动表每页最多加载 200 行，避免十万级记录一次性进入界面。

元数据读取仍会带来少量 I/O。对机械硬盘来说，这类正常读取不会造成特殊损伤，但全盘目录遍历
会增加寻道和短时占用，因此 DiskWatch 默认避免它，并允许关闭或取消启动恢复。

## 可重复的合成基准

仓库提供 `tests/perf_probe.py`，它不会读取真实用户配置、不会启动真实磁盘监控，所有数据都在
临时目录生成并在退出后自动删除：

```powershell
.venv\Scripts\python.exe tests\perf_probe.py --events 100000 --burst 100000
```

基准覆盖同路径事件洪峰合并、10 万条账本的计数与筛选、200 行分页查询以及离屏活动页构造。
具体数字依赖 CPU、磁盘、Python 和 Qt 版本，应在目标 HDD 与 SSD 设备上分别记录；仓库不把
某一台开发机的结果当作所有设备的性能承诺。

## 当前开发机基线

2026-08-29 在 Windows AMD64、Python 3.14.0、PySide6 6.11.1 上运行上述 10 万条场景：

| 场景 | 结果 |
| --- | ---: |
| 10 万次同路径修改提交与合并 | 355.09 ms |
| 实际保留的待处理修改 | 1 条 |
| 写入 10 万条合成账本 | 1.28 s |
| 全量计数 | 6.24 ms |
| 磁盘与分类组合筛选计数 | 27.39 ms |
| 读取最新 200 行 | 0.97 ms |
| 构造并完成 200 行文件活动页后台加载 | 91.23 ms |
| 10 万条合成账本数据库大小 | 25.91 MB |
| 活动页工作集增量 | 4.54 MB |

当前环境无法通过非管理员接口可靠确认承载临时目录的物理介质类型，因此这组数据不标注为
HDD 或 SSD。发布候选版仍需在明确介质类型的 HDD 与 SSD 真机上分别补测空闲 CPU、解压事件洪峰、
长时间内存漂移和 USN 启动恢复耗时。
